- new skill `test-frameworks`, the platform's answer to spine-toolkit's **testing** topic: one section per value of the `tests` axis — XCTest, Swift Testing, Quick+Nimble — each saying how a test is declared so the runner collects it, how it asserts, its lifecycle hooks, parameterization, async, how a failure reads in a run, and what the project needs to run it. Plus the surfaces that force a framework whatever the axis says: XCUITest and `measure` are XCTest
- `swift-tester` writes in the framework the project declared instead of the one its own text knew. Its naming example was the sharpest edge: `methodName_condition_expectedResult()` without the `test` prefix compiles and is never collected by XCTest, so a task could end green with no test in it. The name convention stays; how a runner is made to see it now comes from the section for the project's `- Tests:` value
- `swift-validator` reads the failures of both frameworks. Swift Testing reports through its own channel — `✘ … recorded an issue at File.swift:12:5` — which never appears as `Test Case '…' failed` and is not counted in `Executed N tests, with M failures`; a Swift Testing suite could fail every test and the digest reported a clean run
- the regression test `swift-developer` adds and the sketch `swift-diagnostics` writes follow the same rule, so a BUG task in a Swift Testing project no longer produces XCTest
- `swift-init` asks which test framework a new project uses (default Swift Testing, as the workspace generator already did), carries `--tests=swift-testing|xctest|quick-nimble`, passes the answer on so setup does not ask again, and writes the placeholder test and its package dependencies from the skill
- the floor on core moves to `>=2.5.0 <3`: the agents name `spine-toolkit:test-authoring`, which is the rule that picks the framework, and it exists from that release
