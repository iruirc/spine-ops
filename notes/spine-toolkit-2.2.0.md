- RESEARCH can answer by an experiment. A task whose `Task.md` carries `[RESEARCH_EXPERIMENT] = [on]` lets its Research agent change code on a branch `experiment/<task>` cut in the current checkout, build it, run the app on a simulator or emulator created for the experiment or as a local process, and drive it through the project's driver. Nothing from the branch is merged: every checkout goes back to the branch or commit it was on, and `Research.md` → `### Experiment` names the branch together with the steps that repeat the run and the files it left in `experiment/`. Every finding says whether a run or reasoning backs it
- nothing is discarded to restore a checkout: `git clean`, `git restore .`, `git reset --hard`, `git stash` and forced switches are forbidden, and while a checkout holding the task folder is on the experiment branch nothing is written into that folder
- the permission reaches the agent only as the contract field `research_experiment=on|off`, never from the task's prose. Without the line RESEARCH runs exactly as before, brief and schema unchanged
- a Research stage whose experiment did not finish returns `ask_user` before the next stage, with its reason; one that left a checkout on the experiment branch stops and says which
- the orchestrator announces the experiment at every `[PROGRESS]` value, `quiet` included, and runs the driver pre-flight for it; the driver warnings name the experiment as well as Validation
- an epic never pushes a RESEARCH step with `[RESEARCH_EXPERIMENT] = [on]`: it and the steps after it come back as `pending_steps`, so the orchestrator announces and gates it. A pushed RESEARCH step now gets its own `[RESEARCH_AGENT]`; before, it always ran with the architect
- `task-new` writes the line when a request for a RESEARCH task asks for the answer by running something; `conventions/research-vs-epic.md` sends a spike there
- the reference driver floor moves with this release; nothing the platforms vendor moved, so none of them has to re-vendor
