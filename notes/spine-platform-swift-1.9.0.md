- one DI rule across `di-module-assembly`, `di-composition-root`, `di-swinject`, `di-factory` and `swift-init`: the `AppDependencyContainer` facade and its dependency protocols are `@MainActor`, and background work gets its services at bootstrap instead of resolving them. Swinject registers only services, and the module's `*Assembly` builds ViewModels and views; Factory's `@Injected` and `Container.shared` resolve only at the composition edge — the `@main` App, the scene delegate, the root view
- `di-module-assembly` names both ends of the chain: a coordinator on UIKit and AppKit, and on SwiftUI the view that owns the root `NavigationStack`, building each screen inside `navigationDestination`
- code written from the earlier samples — a nonisolated container that background work resolves from, ViewModels registered in Swinject, `@Injected` in ViewModels or services — is now what the reviewer and refactorer agents flag
- `concurrency-architecture` names the two target settings that decide where a `nonisolated async` body runs, `SWIFT_APPROACHABLE_CONCURRENCY` and `SWIFT_DEFAULT_ACTOR_ISOLATION`, and which of them Xcode 26 templates and `swift-init` projects use; the UI-role protocols of `arch-coordinator` and `arch-viper` are `@MainActor`
- `persistence-architecture`: `@Query` / `@FetchRequest` in a View is one named exception, a read-only list with no business rule, and Pattern A loads the Core Data store in the Composition Root's warm-up and fails on a load error; `persistence-migrations`: renaming an entity is a lightweight migration
- `nav-deeplinks`: an unknown link leaves navigation where it is; `net-architecture`: the API client returns DTOs and the repository maps them to Domain; `arch-mvi`: the reducer takes its dependencies as parameters
