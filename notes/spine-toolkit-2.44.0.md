- a project keeps a registry of known test failures, `Tasks/KnownFailures.md` by default; `- Known failures: <path>` in `## Paths` moves it, a leading `/` and a plain path from the project root, `~` expanded. `resolve-settings.sh json` prints it as `known_failures`, the contract carries it, an epic hands it to each step. A missing file is an empty registry. The format, `## Removed` and who writes it: `conventions/known-failures.md`
- Validation classifies every failing test by `phase-verification` → `### Failures outside the task`: a test that does not reach the symbols the task's diff changed is outside the task. A `permanent` entry still failing, or a `flaky` entry green on its retry, leaves `PASSED`; an unregistered outside failure green on a retry of its classes, up to three times and with no second full run, gives the new status `PASSED_WITH_FLAKES`; a red retry or a failure inside the task is `FAILED`, whatever the registry says. `FLAKY` stays with a TEST task's own added tests. `Validation.md` lists them under `## Outside the task`; the return carries `outside_failures` and `known_failures_cleared`
- `PASSED_WITH_FLAKES` passes the Validation gate in every profile, an epic's step verdict and its Acceptance, with the note `Validation passed with <n> flake(s) outside the task.`; Validation writes `[VALIDATED_COMMIT]` on it as on `PASSED`, and `lint-validation-scope.sh` reads it so
- in manual the orchestrator prints the flaky and red failures outside the task and offers to add them to the registry, as `flaky` after `PASSED_WITH_FLAKES`, as `permanent` and a cheap repeat of Validation after a `FAILED` caused only by them; a `permanent` entry that passed is offered for removal as a question of its own. Only on the owner's word: the rows go in a commit of their own and the decision into `Questions.md`. In auto the registry never changes
- Validation carries a module from any green whole-module run its commits since do not reach: a phase records each such run as a `ran:` line under its check in `Plan.md` after its commit, written `carried <sha> (phase <N>)`, and a green row of an earlier `Validation.md`, whatever its status, `carried <sha> (validation)`. A module red in the latest Validation that ran it runs again. A first Validation no longer runs the whole set when a phase already ran a module whole
- `lint-validation-scope.sh` accepts the two carried sources; a carried row with later commits in its repository is a `reach` line, not a finding — always for a phase carry, per repository otherwise — and Review confirms each against the diff and the manifests
- `phase-verification`: the tests of the perimeter are every test of the modules a phase edits, the dependents' tests are named by class, and a full test plan of the app or all tests in a phase's checks is a defect of the plan at `proportional`, a project without modules aside. The `Plan.md` reader gets the kind `suite in a phase`
- in manual, before anything of a task has run, the orchestrator's confirmation offers to run a small FEATURE, BUG or REFACTOR at `lite` when its scale came from the project config or the default; yes writes `[SCALE] = [lite]` into `Task.md`. Never in auto, never when the command named profile and mode
